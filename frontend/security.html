Security

How Saple is protected

This page describes the controls that are actually implemented in this repository, and how to tell the project owner about a problem.

Saple is an independent BUET CSE academic project for company and career insights. It is not affiliated with, endorsed by, or an official login or careers service for any company named on the site.

Authentication and sessions

Passwords are hashed with BCrypt at cost 12 and are never stored or emailed in readable form.

Sessions use a signed JWT with a fixed issuer, audience and algorithm. Every protected request reloads the account’s status, role, token version and company assignments from PostgreSQL, so a suspended account, a revoked assignment or a password change takes effect immediately rather than when the token happens to expire.

Authorization

Permissions are enforced in middleware, in the service layer and in SQL. Nothing depends on a hidden button.

A company representative is bound to explicit company assignments. A request for another company’s vacancy, application or verification fails on the server with the same message whichever company it was, so responses cannot be used to map who represents whom.

Browser hardening

Every response, including static pages and errors, carries explicit headers:

  • A restrictive Content-Security-Policy limiting scripts, styles, images, fonts and connections to this origin, with no unsafe-inline and no unsafe-eval.
  • frame-ancestors none and X-Frame-Options DENY, so Saple cannot be framed.
  • X-Content-Type-Options, Referrer-Policy, Permissions-Policy and cross-origin isolation headers.
  • HTTP Strict Transport Security, sent only over real HTTPS.

No third-party code

Saple loads no remote script, stylesheet, font, iframe or tracker. Earlier versions fetched company logos from an external service using a domain taken from the database; that was removed, and company marks are now generated locally from the company name.

There is no eval, no dynamically constructed code, no URL shortener and no redirect that accepts a destination from a request.

Input and abuse controls

Every input is validated and length-limited, and every database query is parameterised.

Sign-in, registration, password recovery, reports, verification requests, job applications, representative requests and the Saple Guide each have their own conservative rate limit with a plain 429 answer.

Request bodies are capped, and a malformed or oversized body returns the normal JSON envelope rather than a stack trace.

Password recovery

Reset tokens are cryptographically random, stored only as a SHA-256 hash, single-use and short-lived. Issuing a new one revokes the previous ones.

Completing a reset replaces the password, consumes the token and increments the account’s token version in one transaction, which signs out other sessions.

The reset page takes the token out of the visible address and out of browser history before doing anything else.

Reporting a security problem

If you find a vulnerability, please report it privately and give the project owner a chance to fix it before sharing details.

A machine-readable contact is published at /.well-known/security.txt. It is filled from the owner’s SECURITY_CONTACT setting; when that is not configured, no address is invented and the file says so. In that case, open an issue in the project repository linked from the About page without including exploit details.

Please do not run automated scanners, load tests or denial-of-service attempts against a deployment. This is a student project on a free hosting plan.

Known limitations

Stated plainly, because an academic project should not overclaim:

  • Rate limits are per process. A multi-instance deployment would need a shared store.
  • Employment verification reviews a claim and a reference; it does not send or check a real one-time code to a company mailbox.
  • There is no automated malware or content scanning beyond the validation and moderation described above.
  • Sign-in error messages distinguish an unknown address from a wrong password, which is a deliberate usability choice for this project and does reveal whether an address is registered. Password recovery does not.
