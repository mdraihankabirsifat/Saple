# Saple Relational Schema

This document describes the **active PostgreSQL schema** used by the Express
backend on Supabase: `database/postgres/01_final_schema_postgres.sql`, reached
on an existing project by the four migrations in
`database/postgres/migrations/`. It has **21 tables and 5 views**.

Primary keys are marked **PK**, foreign keys **FK**, and unique keys **UK**.
Every single-column surrogate key is `BIGINT GENERATED BY DEFAULT AS IDENTITY`;
the demonstration data uses explicit IDs and then synchronises every identity
sequence with `setval(pg_get_serial_sequence(...))`.

The Oracle 19c files under `database/sql/` are the preserved earlier course
milestone (14 tables, 4 views). They are not used by the running application.
See the final section for how the two relate.

---

## 1. Accounts and identity

- `users` (`user_id` **PK**, `full_name`, `email` **UK**, `password_hash`,
  `user_type`, `account_role`, `account_status`, `token_version`, `created_at`,
  `updated_at`)
- `employees` (`employee_id` **PK**, `user_id` **FK/UK** → users, `employment_status`, `created_at`)
- `password_reset_tokens` (`reset_token_id` **PK**, `user_id` **FK** → users,
  `token_hash` **UK**, `expires_at`, `used_at`, `revoked_at`, `created_at`)

`user_type` (`NORMAL` | `EMPLOYEE`) says what kind of person the account
belongs to. `account_role` (`USER` | `ADMIN` | `COMPANY_REPRESENTATIVE`) is
independent authorization. Registration always writes `USER`; the
representative role is set only when an administrator approves an assignment
(section 5) and is removed when the last active assignment closes. `ADMIN` is
assigned directly in the database by the owner.

`token_version` is incremented on logout, password change, password reset and
any representative-role change; a JWT carrying an older version is refused, so
sessions are revocable.

Reset tokens store only a 64-character SHA-256 hash, expire, and are single-use:
`used_at` and `revoked_at` are mutually exclusive.

## 2. Company reference data

- `companies` (`company_id` **PK**, `company_name` **UK**, `industry`,
  `headquarters_city`, `country`, `website`, `company_size`, `description`,
  `created_at`, `updated_at`)
- `job_roles` (`role_id` **PK**, `role_name` **UK**, `role_category`, `description`)
- `benefits` (`benefit_id` **PK**, `benefit_name` **UK**, `benefit_category`, `description`)
- `company_benefits` (`company_id` **PK/FK**, `benefit_id` **PK/FK**, `details`,
  `eligibility`, `last_updated`)

`company_benefits` resolves the many-to-many relationship between companies and
benefits. `companies.website` is displayed as text only; the browser never
fetches anything derived from it.

## 3. Employment verification

- `employment_verifications` (`verification_id` **PK**, `employee_id` **FK** →
  employees, `company_id` **FK** → companies, `role_id` **FK** → job_roles
  (nullable for legacy rows only), `verification_method`, `company_email`,
  `proof_type`, `proof_reference`, `verification_status`, `requested_at`,
  `reviewed_at`, `expires_at`, `rejection_reason`, `reviewed_by` **FK** → users)

Trust is scoped to the exact employee + company + role tuple. A row with no
role authorizes nothing.

- **Current employees** use `COMPANY_EMAIL_OTP`: only the company email address
  is stored. No code is sent and no one-time value is stored — the method name
  records the intended mechanism, which is out of scope.
- **Former employees** use `DOCUMENT`: only a short proof type and a safe
  reference string are stored. No file is uploaded.

`ck_emp_verify_review` ties reviewer identity to status: a `PENDING` row has no
reviewer; any decided row has both reviewer and time. Rejection requires a
reason. Verified rows expire after 12 months.

**Who decides:** an `ACTIVE` company representative assigned to that company,
through the representative workspace; administrators keep oversight and can
decide any request as a fallback or escalation. Both paths write the same
`reviewed_by` column and notify the employee.

## 4. Submissions (supertype / subtype)

- `submissions` (`submission_id` **PK**, `user_id` **FK** → users, `company_id`
  **FK** → companies, `submission_type`, `is_anonymous`, `submission_status`,
  `verification_status`, `submitted_at`, `approved_at`, `updated_at`)
- `salary_submissions` (`submission_id` **PK/FK**, `role_id` **FK**,
  `base_salary`, `additional_compensation`, `currency`, `pay_period`,
  `years_of_experience`, `employment_type`, `work_mode`, `salary_year`)
- `company_reviews` (`submission_id` **PK/FK**, `role_id` **FK**, `review_title`,
  five rating columns, `pros`, `cons`, `advice_to_management`,
  `employment_status`, `review_date`)
- `interview_experiences` (`submission_id` **PK/FK**, `role_id` **FK**,
  `interview_date`, `difficulty_level`, `rounds_count`, `interview_mode`,
  `result_status`, `duration_days`, `process_description`, `questions_summary`)

Each subtype uses the parent's `submission_id` as both PK and FK
(total, disjoint specialization on `submission_type`). Subtype-to-type
consistency is enforced by the repositories, which write parent and child in
one transaction, because a `CHECK` constraint cannot inspect another table.

Anonymous submissions keep their internal `user_id` for accountability; no
public view exposes it. `ck_submissions_approved_at` ties `approved_at` to the
`APPROVED` status.

## 5. Company representatives

- `company_representatives` (`assignment_id` **PK**, `user_id` **FK** → users,
  `company_id` **FK** → companies, `job_title`, `assignment_status`,
  `request_note`, `decision_note`, `approved_by` **FK** → users, `approved_at`,
  `revoked_by` **FK** → users, `revoked_at`, `created_at`, `updated_at`)
- `representative_assignment_actions` (`action_id` **PK**, `assignment_id`
  **FK** → company_representatives, `actor_user_id` **FK** → users,
  `action_type`, `previous_status`, `new_status`, `action_note`, `action_at`)

A representative is an ordinary account bound to one or more companies through
this association table. One company may have many representatives.

- **Partial unique index** `uk_company_rep_open_scope` on
  (`user_id`, `company_id`) `WHERE assignment_status IN ('PENDING','ACTIVE')`:
  at most one open or active scope per account and company, while rejected and
  revoked rows stay for audit.
- `ck_company_rep_approval`: `ACTIVE` and `REVOKED` rows always carry
  `approved_by` and `approved_at`; `PENDING` and `REJECTED` rows never do.
- `ck_company_rep_revocation`: only a `REVOKED` row carries revocation identity.
- `ck_company_rep_decision_note`: rejection and revocation require a note.

Every request, approval, rejection and revocation appends one immutable row to
`representative_assignment_actions`.

## 6. Jobs and applications

- `job_postings` (`job_id` **PK**, `company_id` **FK** → companies,
  `created_by_user_id` **FK** → users, `created_by_assignment_id` **FK** →
  company_representatives, `role_id` **FK** → job_roles (optional), `title`,
  `description`, `requirements`, `location`, `employment_type`, `work_mode`,
  `salary_min`, `salary_max`, `salary_currency`, `salary_period`,
  `application_deadline`, `job_status`, `published_at`, `closed_at`,
  `created_at`, `updated_at`)
- `job_applications` (`application_id` **PK**, `job_id` **FK** → job_postings,
  `applicant_user_id` **FK** → users, `cover_letter`, `application_status`,
  `submitted_at`, `updated_at`, `reviewed_by` **FK** → users, `reviewed_at`),
  with (`job_id`, `applicant_user_id`) **UK**
- `job_application_status_history` (`history_id` **PK**, `application_id` **FK**
  → job_applications, `actor_user_id` **FK** → users, `previous_status`,
  `new_status`, `action_note`, `action_at`)

Constraints on `job_postings`:

- `ck_job_salary_range`: either all four salary columns are null, or all four
  are present with `salary_min > 0` and `salary_max >= salary_min`.
- `ck_job_published_at`: a `DRAFT` has no `published_at`; every other status
  has one.
- `ck_job_closed_at`: `CLOSED` and `ARCHIVED` have `closed_at`; the others do not.
- `ck_job_description`: at least 20 non-blank characters.

Constraints on `job_applications`:

- One application per account and job (**UK**).
- `ck_application_review`: `SUBMITTED` and `WITHDRAWN` carry no reviewer;
  `UNDER_REVIEW`, `SHORTLISTED`, `REJECTED` and `ACCEPTED` always do.
- `ck_application_cover_letter`: 30–4,000 characters.
- There is deliberately **no resume or attachment column**: Saple accepts no
  file uploads and never fetches an applicant-supplied URL.

Applications and their history reference their parents with
`ON DELETE RESTRICT`, so closing or archiving a vacancy can never destroy an
application or its decision trail.

## 7. Announcements and notifications

- `announcements` (`announcement_id` **PK**, `title`, `message`, `severity`,
  `is_dismissible`, `is_active`, `starts_at`, `ends_at`, `created_by` **FK** →
  users, `created_at`, `updated_at`)
- `notifications` (`notification_id` **PK**, `user_id` **FK** → users,
  `notification_type`, `title`, `message`, `related_entity_type`,
  `related_entity_id`, `read_at`, `created_at`)

Both tables reject `<` and `>` in title and message
(`ck_*_plain_text`), so stored text can never become markup. The browser also
renders them with `textContent`.

A notification belongs to exactly one account (`ON DELETE CASCADE` from users,
because it is private data of that account). `ck_notifications_entity` allows
either no related entity, or one of a fixed set of kinds with a positive ID.
The partial index `ix_notifications_unread` makes the unread count cheap.

## 8. Reporting and moderation

- `reports` (`report_id` **PK**, `reporter_user_id` **FK**, `submission_id` **FK**,
  `reason_category`, `report_description`, `report_status`, `reported_at`,
  `resolved_at`, `resolution_note`, `resolved_by` **FK**), with
  (`reporter_user_id`, `submission_id`) **UK**
- `moderation_actions` (`action_id` **PK**, `submission_id` **FK**,
  `moderator_user_id` **FK**, `action_type`, `previous_status`, `new_status`,
  `action_note`, `action_at`)

One report per account and submission. Moderation actions are the append-only
history of every submission status change. The column is still named
`moderator_user_id` for compatibility; the actor is always an administrator.

## 9. Views

| View | Purpose |
|------|---------|
| `vw_public_companies` | Public company profile columns |
| `vw_public_approved_reviews` | Approved reviews, no submitter identity |
| `vw_verified_salary_summary` | Ranges from `APPROVED` **and** `VERIFIED` salaries |
| `vw_community_salary_summary` | Ranges from all `APPROVED` salaries |
| `vw_public_open_jobs` | `PUBLISHED` vacancies with `application_deadline >= CURRENT_DATE` |

Aggregates are always derived, never stored. `vw_public_open_jobs` exposes no
creator, assignment, applicant or application data; every public job query
reads it rather than the base table.

## 10. Relationships and cardinalities

| From | To | Cardinality | Delete rule |
|------|----|-------------|-------------|
| users | employees | 1 : 0..1 | cascade |
| users | password_reset_tokens | 1 : 0..* | cascade |
| employees | employment_verifications | 1 : 0..* | cascade |
| companies | employment_verifications | 1 : 0..* | cascade |
| job_roles | employment_verifications | 1 : 0..* | no action |
| users | submissions | 1 : 0..* | no action |
| companies | submissions | 1 : 0..* | no action |
| submissions | salary / review / interview subtype | 1 : 0..1 each (exactly one in practice) | cascade |
| submissions | reports | 1 : 0..* | cascade |
| submissions | moderation_actions | 1 : 0..* | cascade |
| companies ↔ benefits | company_benefits | M : N | cascade |
| users | company_representatives | 1 : 0..* | cascade |
| companies | company_representatives | 1 : 0..* | **restrict** |
| company_representatives | representative_assignment_actions | 1 : 1..* | **restrict** |
| companies | job_postings | 1 : 0..* | **restrict** |
| company_representatives | job_postings | 1 : 0..* | set null |
| job_roles | job_postings | 1 : 0..* | no action |
| job_postings | job_applications | 1 : 0..* | **restrict** |
| users | job_applications | 1 : 0..* | no action |
| job_applications | job_application_status_history | 1 : 1..* | **restrict** |
| users | announcements (author) | 1 : 0..* | no action |
| users | notifications | 1 : 0..* | cascade |

Every table added in this upgrade uses `RESTRICT` or `NO ACTION` for audit and
application relationships. `CASCADE` is used only where a row is private data
of one account.

## 11. Status transitions

| Entity | Transitions (who) |
|--------|-------------------|
| Submission | `PENDING → APPROVED \| REJECTED \| FLAGGED`; `APPROVED → REJECTED \| FLAGGED`; `FLAGGED → REJECTED` (admin; note required except for approval) |
| Verification | `PENDING → VERIFIED \| REJECTED` (assigned representative or admin; reason required to reject). A `VERIFIED` row stops authorizing contributions once `expires_at` (12 months) passes; the `EXPIRED` value exists in the CHECK but no job sets it automatically |
| Report | `OPEN → REVIEWING`; `OPEN \| REVIEWING → RESOLVED \| DISMISSED` (admin; note required to close) |
| Representative assignment | `PENDING → ACTIVE \| REJECTED`; `ACTIVE → REVOKED` (admin; note required to reject or revoke) |
| Job posting | `DRAFT → PUBLISHED → CLOSED → ARCHIVED` (assigned representative; admin may close for safety) |
| Application (reviewer) | `SUBMITTED → UNDER_REVIEW \| SHORTLISTED \| ACCEPTED \| REJECTED`; `UNDER_REVIEW → SHORTLISTED \| ACCEPTED \| REJECTED`; `SHORTLISTED → ACCEPTED \| REJECTED` (note required to accept or reject) |
| Application (applicant) | `SUBMITTED \| UNDER_REVIEW \| SHORTLISTED → WITHDRAWN` |

`REJECTED`, `ACCEPTED`, `WITHDRAWN`, `REVOKED` and `ARCHIVED` are terminal.
Every transition is made inside one transaction with a `SELECT ... FOR UPDATE`
on the row, the status change, its history row and any notification.

## 12. Installing

- **Fresh project:** run `01_final_schema_postgres.sql`, then optionally
  `02_final_demo_data_postgres.sql`, then the read-only
  `03_schema_and_data_demo_postgres.sql`.
- **Existing project:** run migrations `001` to `004` in order (see
  `database/postgres/migrations/README.md`), then the read-only validation.

Both paths reach the same 21 tables and 5 views;
`backend/tests/schema-migrations.test.js` checks that every table, constraint
and index in the migrations also exists in the fresh schema.

## 13. The Oracle milestone

`database/sql/` holds the Oracle 19c version delivered at the earlier
milestone: the 14 original tables and 4 views, using Oracle types
(`VARCHAR2`, `NUMBER`, `SYSTIMESTAMP`, `MERGE`). It is kept unchanged as a
record of that milestone. The seven tables and one view added in this upgrade
exist only in PostgreSQL; no Oracle parity migration is provided, because the
Oracle files are not a runtime and the course deliverable for this phase is the
PostgreSQL implementation.
