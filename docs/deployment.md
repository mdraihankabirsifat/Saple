# Render and Supabase Deployment

Saple is deployed as one Render Node web service. Express serves both the existing static frontend and every `/api` endpoint, while the server connects privately to the existing Supabase PostgreSQL database through `pg`.

```text
Browser
   |
   | HTTPS, one origin
   v
Render web service (Express API + frontend files)
   |
   | DATABASE_URL, raw parameterized SQL
   v
Supabase PostgreSQL
```

The browser does not use Supabase Auth, the Supabase JavaScript client, an anon key, a service-role key, or a database connection string.

## 1. Prepare Supabase only if it is fresh

Do not run schema or seed files against an existing populated project. They create and populate the Saple model and are intended for a fresh database.

For a confirmed fresh project, open the Supabase SQL editor and execute:

1. `database/postgres/01_final_schema_postgres.sql`
2. `database/postgres/02_final_demo_data_postgres.sql`
3. `database/postgres/03_schema_and_data_demo_postgres.sql`

The third file is read-only validation. Do not rerun the first two files merely to deploy the application.

## 2. Copy the Supabase connection string

In the Supabase dashboard, open the project and click **Connect**. Copy the exact connection string supplied there and replace its password placeholder privately.

For a persistent Render web service on an IPv4 network, prefer the **Session pooler** string when a direct connection is unsuitable. The shared Session pooler commonly uses port `5432`; use the exact hostname, region, username, and encoded password that Supabase provides. Keep `DB_SSL=true` and use a conservative application pool.

Never put this value in Git, `render.yaml`, frontend code, documentation, screenshots, or logs.

Supabase connection guidance: <https://supabase.com/docs/guides/database/connecting-to-postgres>

## 3. Push the repository to GitHub

Review and commit the hosting changes locally, then push the intended branch:

```powershell
git status
git diff --check
git add -p
git add render.yaml backend/config/hosting.js backend/tests/hosting.test.js docs/deployment.md
git diff --cached
git commit -m "prepare Saple for Render hosting"
git push origin main
```

Inspect `git diff --cached` before committing. Do not add `backend/.env`.

## 4. Create the Render Blueprint

1. Sign in to Render and connect the GitHub account that can access the Saple repository.
2. Choose **New > Blueprint**.
3. Select this repository and its root `render.yaml`.
4. Review the single `saple` Node web service. The Blueprint does not create Render Postgres or a persistent disk.
5. Enter `DATABASE_URL` when Render prompts for the private `sync: false` value.
6. Let Render generate `JWT_SECRET`; do not replace it with a weak fixed value.
7. Apply the Blueprint and watch the build/deploy logs.

The Blueprint installs production dependencies from `backend/package-lock.json`, starts `backend/server.js`, deploys on commits to the connected branch, and checks `/api/health`.

Render Blueprint reference: <https://render.com/docs/blueprint-spec>

## 5. Render environment values

The Blueprint safely supplies these non-secret settings:

- `DB_SSL=true`
- `DB_POOL_MAX=5`
- `DB_IDLE_TIMEOUT_MS=30000`
- `DB_CONNECTION_TIMEOUT_MS=10000`
- `JWT_EXPIRES_IN=1d`
- `PASSWORD_RESET_TOKEN_TTL_MINUTES=15`

The required secret settings are:

- `DATABASE_URL`: enter the exact Supabase connection string in Render.
- `JWT_SECRET`: generated by Render from `generateValue: true`.

Production is same-origin, so `CORS_ORIGINS` is normally unnecessary. If a separate HTTPS frontend is introduced, set it to a comma-separated list of exact allowed origins.

## 6. Verify the deployed service

After Render supplies a domain such as `https://YOUR-SERVICE.onrender.com`, test:

```text
https://YOUR-SERVICE.onrender.com/
https://YOUR-SERVICE.onrender.com/api
https://YOUR-SERVICE.onrender.com/api/health
https://YOUR-SERVICE.onrender.com/api/health/database
https://YOUR-SERVICE.onrender.com/api/companies
https://YOUR-SERVICE.onrender.com/api/job-roles
```

The root must show the Saple homepage. `/api` must return the API welcome response. Test registration, login, authenticated profile access, logout, and rejection of the old JWT before treating the deployment as verified.

## 7. Provision private demonstration users

Render Free services do not provide shell access. To provision the three demonstration accounts, use the existing script locally while your ignored `backend/.env` points to the same Supabase project:

```env
DEMO_NORMAL_PASSWORD=choose_a_private_password
DEMO_EMPLOYEE_PASSWORD=choose_a_private_password
DEMO_ADMIN_PASSWORD=choose_a_private_password
```

Then run:

```powershell
cd backend
npm run provision:demo-users
```

Optional demo email overrides are listed in `backend/.env.example`. The script hashes passwords and does not print them. Remove private demo variables from the local environment when they are no longer needed.

## 8. Run the live integration workflow

From a trusted local machine, configure the ignored `backend/.env` with the deployed Supabase `DATABASE_URL` and a test `JWT_SECRET`, then run:

```powershell
cd backend
npm ci
npm test
npm run test:integration
```

The integration workflow creates temporary records and cleans them up. It verifies the database directly; it does not test the public Render URL.

## 9. Configure password-reset email later

Forgot-password email requires these private Render environment values:

```text
SMTP_HOST
SMTP_PORT
SMTP_SECURE
SMTP_USER
SMTP_PASS
SMTP_FROM
```

Do not set placeholder SMTP values in production. Without valid SMTP configuration, only the forgot-password delivery feature is unavailable; other application routes remain usable.

When `FRONTEND_URL` is absent on Render, reset links use Render's trusted `RENDER_EXTERNAL_URL`. When adding a custom domain, set `FRONTEND_URL` to that public HTTPS origin, for example `https://saple.example.com/`. URLs with embedded credentials are rejected.

Render environment reference: <https://render.com/docs/environment-variables>

## 10. Free-service cold starts

Render currently spins down a Free web service after 15 minutes without inbound traffic. The next request starts it again and can take about one minute, during which Render shows a loading page. That delay is a hosting-plan limitation, not a Saple API or Supabase defect. Free-service filesystem changes are ephemeral; Saple durable data remains in Supabase.

Render Free service limitations: <https://render.com/docs/free>
